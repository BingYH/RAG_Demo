# 中文讲稿

这是[英文讲稿](../speaker_notes.md)的独立中文版，用于理解和排练。现场只讲一种语言；十分钟以内的时间安排以英文讲述为基准，中文讲述需要单独计时。

把这些内容当作提示，不必逐字朗读。时间安排参照[展示流程](run_of_show.md)。主案例是合成数据上的 PD 排障演示，不代表完成了实体机械臂验证，也不声称能够自主修复。

## 0:00 — 工程问题

我围绕一个测试工程问题搭建了这个演示：当关节响应测试不通过时，怎样把测试结果转化为有证据支持的下一步行动？

这个例子使用简化的离线 PD 模型，没有积分项。数据和验收阈值都是为演示独立设计的。我的重点是工程处理过程：可衡量的要求、可复现的证据、结构化调查，以及向负责工程师提供有用的反馈。

## 0:40 — 评价响应结果

目标位置变为 0.2 弧度。实际响应先出现超调和振荡，随后才稳定下来。Python 从保存的轨迹中计算指标：超调为 58.53%，要求不超过 5%；调节时间为 2.56 秒，要求不超过 1.5 秒。

末段误差虽然通过，但不代表整个测试通过，因为瞬态响应同样重要。我让数值要求的判定由确定性代码完成，不让语言模型决定测量值是否满足阈值。结论只适用于这一个关节、这一次动作和这份记录。

## 1:35 — 调查控制配置

接下来，我把本次测试配置与登记的基准配置进行比较。记录显示 Kd 从 0.85 改成了 0.10。在这个 PD 模型中，微分反馈提供速度阻尼，因此较低的 Kd 是解释当前振荡现象时值得优先核查的假设。

我会核查为什么修改这个参数，以及测试条件是否具有可比性。我不会从一个合理解释直接跳到唯一根因。在实际调查中，负载、配置和测量条件都可能影响判断。这份报告提出验证建议，不会给控制器调参，也不会宣称问题已经修复。

## 2:40 — 展示支持证据

这里可以查看原始配置字段以及相关测试规程。两者的作用不同：观测记录说明本次记录到了什么，规程则解释指标的定义和比较规则。

模型选择事实 ID，应用程序再从工具返回的字段中生成数值和引用，并明确区分登记值与当前值。这能避免一部分来源对应错误，但不能证明所有推断都正确，因此还有独立的复核步骤检查解释和追问。

## 3:35 — 处理信息缺失

这是另一个测试，负载记录不完整。虽然响应仍有可以量化的偏差，但我不能假设当前负载与登记基准相同，再据此解释异常。工作流会暂停，询问使用了什么工具和负载，以及是否发生过更换。

这个分支在请求模型之前就由证据检查决定。如果现场人员不知道，回答“不知道”也是有效信息。原始缺失值仍然保持缺失；用户的说明只作为未经验证的背景信息保存。

## 4:35 — 继续形成有用的技术支持

现在我会打开另一个此前已执行的 WSL ROS 案例，展示后续处理过程，避免现场等待新的模型运行。它的报告仍保留负载和惯量记录缺失的问题。工单草稿包含测试标识、已完成检查、引用、待解决事项和支持请求。

工程师可以修改文字并审阅完整草稿。创建工单必须明确批准当前这一版内容。修改会改变哈希，因此需要重新批准。对已批准内容重复执行创建会返回同一份本地工单，不会产生重复记录。这里我会把演示草稿保留在未批准状态。

## 5:35 — 解释工程集成

架构为每个部分安排了明确职责。Python 生成离线轨迹、计算指标并校验证据。在 ROS 模式下，WSL 中的发布节点发送采样点，订阅节点收集完整快照。Windows 通过 HTTP 读取，检查身份和完整性，并重新计算指标。这里是真实的 ROS 通信传输合成数据，不是新的传感器实测。

RAG 检索适用规程，Claude 解释事实并提出调查建议，LangGraph 管理分支、暂停、有界重试和审批，Dashboard 展示结果。这样就把确定性脚本、跨系统接口和 AI 辅助组织成了一条可以检查的工作流。

## 6:45 — 检查执行过程

这是预先准备的一次历史运行的 Trace。我们可以查看报告生成、校验和复核，也能看到工作流在哪里暂停。复核失败可以触发一次纠正；如果仍然失败，就转人工处理，而不是无限循环。

LangSmith 帮助我调查应用程序自身的行为：哪些证据送进了模型、执行了哪条路径，以及记录了多少延迟和 Token 用量。这是执行过程的可观测性，不是查看模型内部的思考过程。

## 7:45 — 工程下一步与个人贡献

我建议的下一步是进行受控比较：确认变更意图，核查规程和负载条件，取得测试配置批准，然后采集一次新的运行，用相同指标进行比较。这个演示没有执行实体复测。另一条基准曲线只是参考资料，不能作为问题已经修复的证据。

我希望为这个岗位展示的是测试软件、数据分析和技术支持之间的衔接能力。我可以把要求转成检查，保留证据，解释不确定性，并整理出有用的下一步行动。AI 帮助组织调查，而计算与工程审批始终明确可查。

## 技术追问：不计入主讲时间

**为什么使用 PD，而不是完整的 PID？**

这样可以用容易理解的例子单独展示位置反馈和阻尼。Ki 为零，因此不能用积分饱和来解释这里的问题。只有出现明确的测试问题时，我才会进一步扩展模型。

**为什么不只用 Python？**

Python 适合计算、完整性检查和阈值判定。AI 增加了基于语言的知识检索、解释和用户背景信息处理能力。工作流图把两者协调起来，包括澄清和人工审批。

**为什么选择 LangGraph？**

这个流程有需要保存状态的分支和中断，不只是一次提示词调用。显式节点和检查点让暂停、恢复和有界失败处理都能被检查。如果流程更简单，也可能不需要这么多编排。

**为什么使用 ROS 和 HTTP？**

ROS 用来展示 Linux 侧的数据采集接口，HTTP 则为 Windows 提供一个小而明确的只读边界。AI 层收到的是固定下来的证据，而不是持续变化、没有边界的话题数据流。我没有把 ROS 说成这份 JD 明确要求的技术。

**以后怎样连接真实硬件？**

我会先明确实际采集接口、时间戳、单位、校准、数据完整性和已批准规程，再替换证据适配器，不直接授予模型设备控制权限。仅凭当前演示，不能证明实时性能、现场总线集成或实体设备安全验证已经完成。

**你对系统质量做过哪些衡量？**

仓库中有离线测试，以及数量有限的真实模型回归案例。我可以展示这些检查及其边界，但目前还没有建立通用准确率、实测节省时间或生产可靠性的结论。

**你在项目开发过程中怎样使用 AI？**

我使用 AI 辅助开发，并不断调整工程范围、证据接口和工作流行为。我区分生成出来的实现与经过验证的行为：我需要能够解释设计、检查数据并验证结果。我会如实说明自己的贡献和工具的辅助作用，不会声称每一行代码都是手写的。
